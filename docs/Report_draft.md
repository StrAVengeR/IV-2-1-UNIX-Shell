## Хураангуй
Энэ ажилд Operating System Concepts номын 3-р бүлгийн UNIX Shell төслийг C хэл дээр хэрэгжүүллээ. Shell нь командыг child процесст `fork`/`execvp`-ээр ажиллуулж, `&`-ээр background, `!!`-ээр сүүлийн командыг давтах, `<` `>`-ээр оролт гаралтыг чиглүүлэх, `|`-ээр pipe холбоход зориулагдсан. Shell-ийн үйл явдлыг (процесс үүссэн, дууссан) файлд бичиж, Python локал сервер, HTML UI тэр бүртгэлээс процессын модыг PID-тай нь байгуулна. 22 автомат тестийг Linux (Ubuntu) дээр ажиллуулахад бүгд тэнцсэн. [macOS/бусад орчны үр дүн]. Parser нь энгийн (хашилт, wildcard дэмжихгүй) гэдгийг хязгаарлалтад дурдсан.

## 1. Удиртгал
### 1.1 Зорилго
Shell бол хэрэглэгч ба үйлдлийн системийн цөмийн хоорондох интерфейс. Үүнийг өөрөө бичснээр процесс үүсгэх, программ солих, процесс хүлээх, файл тодорхойлогч (file descriptor) удирдах, pipe ашиглан процесс хоорондын харилцааг практикт ойлгох зорилготой.
### 1.2 Ач холбогдол
`ls | wc -l` гэх мэт нэг мөр команд цаана хэд хэдэн процесс, pipe, fd-ийн дахин чиглүүлэлтээр хэрэгждэг. Үүнийг модоор харуулснаар хийсвэр ойлголт бодит PID-аар харагдана.
### 1.3 Хамрах хүрээ
Хамрах: бүлгийн үндсэн шаардлага, олон шатлалтай pipe, нэг session-тэй UI, автомат тест. Хамрахгүй: хашилт, wildcard, орчны хувьсагчийн тэлэлт, `>>`, `2>`, бүрэн job control, UI-ийн автомат тест.

## 3. Онолын үндэс
### 3.1 Read–Eval–Print давталт
Shell нь мөр уншиж (read), задалж гүйцэтгэж (eval), үр дүнг гаргаад (print) дахин prompt руу буцна.
### 3.2 Системийн дуудлагууд
| Дуудлага | Үүрэг |
|---|---|
| `fork()` | Parent-ийн хуулбар child процесс үүсгэнэ. Child-д 0, parent-д child-ийн PID буцна. |
| `execvp()` | Child-ийн санах ойг шинэ программаар сольно; PATH-аас хайна. |
| `waitpid()` | Parent child дуусахыг хүлээж, exit status авна. |
| `pipe()` | Нэг чиглэлтэй byte урсгал: `fd[0]` унших, `fd[1]` бичих төгсгөл. |
| `dup2(a,b)` | fd `b`-г `a`-тай ижил болгоно. Үүгээр stdin/stdout-ийг файл, pipe руу чиглүүлнэ. |
### 3.3 Zombie процесс
Child дууссан ч parent `wait` хийх хүртэл процессын хүснэгтэд exit status-тайгаа үлддэг. Үүнийг zombie гэнэ. Манай shell background процессыг дараагийн prompt-ийн өмнө `waitpid(-1, WNOHANG)`-аар цуглуулдаг тул тэр хүртэл UI-д `zombie` төлөвтэй харагдана.
### 3.4 Pipe-ийн fd урсгал
`a | b | c` үед shell 2 pipe үүсгэж, `a`-гийн stdout-ыг pipe1-ийн бичих төгсгөлд, `b`-гийн stdin-ыг pipe1-ийн унших төгсгөлд, stdout-ыг pipe2-д, `c`-гийн stdin-ыг pipe2-ийн унших төгсгөлд холбоно. Хэрэггүй fd-үүдийг хаахгүй бол унших тал EOF авахгүй гацдаг.

## 4. Системийн зохиомж
### 4.1 Бүрэлдэхүүн
| Компонент | Файл | Үүрэг |
|---|---|---|
| Shell | `src/osh.c` | parse, fork/exec, pipe, redirection, history, үйл явдлын бүртгэл |
| Сервер | `ui/server.py` | нэг `osh` session-ийг тасралтгүй барьж, HTTP API өгнө |
| UI | `ui/index.html` | терминал, process tree, history |
| Тест | `tests/run_tests.sh` | 22 автомат тест |
### 4.2 Өгөгдлийн урсгал
Хэрэглэгч команд бичнэ → UI `POST /api/run` → сервер `osh`-ийн stdin-д мөр бичнэ → `osh` ажиллуулж гаралтыг stdout руу гаргаад `\x01READY <код>` тэмдэгтээр дууссаныг мэдэгдэнэ → сервер гаралт ба exit code-ыг буцаана. Үүнтэй зэрэг UI 0.8 секунд тутам `GET /api/tree` дуудаж бүртгэлээс мод сэргээнэ.
[ЗУРАГ 4.1: архитектурын схем (Browser → server.py → osh → child процессууд, OSH_LOG файл)]
### 4.3 Үйл явдлын бүртгэл
`OSH_LOG` орчны хувьсагч заасан файлд мөр бүр JSON:
`{"t":мс,"ev":"spawn|exit|shell","pid":..,"ppid":..,"cmd":"..","bg":0|1,"code":..,"seq":..,"line":".."}`
`seq` нь командын дугаар, `line` нь бүтэн мөр. UI процессыг `seq`-ээр бүлэглэнэ.
### 4.4 Төлвийн загвар
`running` → (дуусаад, shell хараахан wait хийгээгүй) `zombie` → (wait хийсэн) `exited <код>`. Бүртгэлд exit байхгүй мөртлөө OS-д PID олдохгүй бол `gone`.

## 5. Хэрэгжилт
### 5.1 Орчин
C11 (`gcc -std=c11 -Wall -Wextra -O2`), POSIX, Python 3 (стандарт сан), HTML/CSS/JS. Гадаад сан ашиглаагүй.
### 5.2 Хязгаар
`MAX_LINE`=1024, `MAX_ARGS`=64, `MAX_STAGES`=16, `MAX_HIST`=100, `MAX_JOBS`=64. Хэтэрвэл тодорхой алдааны мессеж гарна.
### 5.3 Parser
Мөрийг зай, tab болон `|` `<` `>` `&` тэмдэгтээр token болгоно. Тэмдэгтүүд зайгүй бичигдсэн ч (`echo x>f`) таарна. Token бүрийг тусдаа буферт хуулдаг тул тусгаарлагч тэмдэгт устахгүй. Алдаа: pipe-ийн өмнө/дараа команд байхгүй, redirection-ы дараа файл байхгүй, `&` дунд байх.
### 5.4 Гүйцэтгэл (`run`)
Шатлал бүрд `fork`. Child: өмнөх pipe-ийн унших төгсгөлийг stdin-д, дараагийн pipe-ийн бичих төгсгөлийг stdout-д `dup2`-оор холбож, нэмэлт fd-г хааж, `<` `>`-г `open`+`dup2`-оор хэрэгжүүлээд `execvp` хийнэ. Parent: ашиглаж дууссан fd-г хааж, foreground бол бүх child-ийг `waitpid`-ээр хүлээж, сүүлийн шатлалын exit code-ыг хадгална. Background бол `[bg] pid` хэвлээд буцна.
### 5.5 Дотоод командууд
`cd` (pipe-гүй үед shell өөрөө `chdir` хийнэ, учир нь child-д хийвэл parent-д нөлөөлөхгүй), `history` (сүүлийн 10), `!!`, `exit`.
### 5.6 Сервер
Нэг `osh` процессыг `subprocess.Popen`-оор эхлүүлж stdin/stdout-ийг pipe-ээр холбоно. Тусдаа thread нь гаралтыг уншиж `READY` тэмдэгтээр командын хил заана. Хүсэлт бүр түгжээгээр дарааллаар гүйцэтгэгдэнэ. Хамгаалалт: зөвхөн `127.0.0.1:8765`, `Host` толгой шалгана, команд ≤1000 тэмдэгт, 20 секундийн timeout.

## 9. Хэлэлцүүлэг
### 9.1 Үр дүнгийн тайлбар
Бүх автомат тест тэнцсэн нь тестэд хамрагдсан нөхцөлд shell зөв ажиллаж буйг харуулна. Нэг session барьснаар `cd` дараагийн командад нөлөөлдөг болсон. Background процесс дууссаны дараа shell wait хийх хүртэл `zombie`-ээр харагддаг нь онолын ойлголтыг бодитоор харуулдаг.
### 9.2 Хязгаарлалт
- Хашилт (`"a b"`), wildcard (`*`), орчны хувьсагч (`$HOME`), `>>`, `2>`, `!n` хэрэгжээгүй.
- `&` зөвхөн мөрийн төгсгөлд; background-ийн `exit` нь дараагийн prompt-ийн өмнө л бүртгэгдэнэ.
- Process tree нь shell-ийн бүртгэсэн үйл явдал дээр суурилсан; kernel-ийн хүснэгтийг шууд уншдаггүй. Төлвийг `ps`-ээр нэмж шалгана.
- UI, сервер автомат тестээр хамрагдаагүй; гараар шалгасан.
- Windows-д шууд ажиллахгүй (WSL хэрэгтэй).
- Тест нь бүх оролтод алдаагүй гэсэн баталгаа биш.
